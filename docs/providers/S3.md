# S3-Compatible Object Storage (engine doc)

| | |
|---|---|
| **Provider IDs** | `aws-s3`, `minio`, `generic-s3` (and every other object-storage preset: see its own short doc) |
| **Maturity** | Stable |
| **Backend** | restic's native `s3` backend (not rclone) |
| **Auth** | Access key ID + secret access key |
| **Headless** | Direct — no browser involved at all |

**This is the one engine behind every S3-compatible preset** — Backblaze B2,
Wasabi, IDrive e2, Cloudflare R2, Hetzner Object Storage, DigitalOcean
Spaces, Storj, MEGA S4, MinIO, and Amazon S3 itself all go through the exact
same code (`internal/backend`, provider `Backend: s3`). A preset only
supplies a default endpoint and this documentation; there is no
provider-specific S3 implementation to maintain per vendor. If your provider
isn't listed by name, use `generic-s3` — it's the same engine with no
preset defaults.

## Why native, not rclone

restic's own `s3` backend talks to any S3-compatible API directly
(`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` environment variables + a
`s3:https://endpoint/bucket/path` repository spec). Routing this through
rclone would add a layer with no benefit for a protocol restic already
supports natively and maturely.

## What you need

- An endpoint URL (empty/default for AWS S3 itself; required for every other preset — see that preset's own doc for its exact hostname pattern)
- A region (some providers ignore this; set it anyway if given one)
- A bucket name
- An access key ID and secret access key, scoped to that bucket only if your provider supports scoped keys (recommended: least privilege)

## Setting it up

```bash
abm storage add --provider generic-s3 --name backblaze \
    --endpoint s3.us-west-002.backblazeb2.com \
    --region us-west-002 \
    --access-key <your-access-key-id> \
    --secret-key <your-secret-access-key>
```

(Or `--provider backblaze-b2`, `--provider wasabi`, etc. — same flags, a
preset just pre-fills the endpoint default. See `abm storage providers` for
the full list.)

Credentials are stored via the secret store, never in `config.yaml`.

> Passing `--secret-key` on the command line puts it in shell history for
> the duration of your terminal session; prefer running this command from a
> script that reads the key from a file or secret manager where practical.

## Testing

```bash
abm storage test backblaze
```

## Object Lock / immutability

**For ransomware/stolen-credential resilience, use a destination with
Object Lock / WORM (Write Once, Read Many) support.** See
[../IMMUTABILITY.md](../IMMUTABILITY.md) for the full picture, including the
important nuance that Object Lock changes how `restic prune` can behave —
enabling it is not a drop-in, zero-tradeoff switch.

Enabling Object Lock is done on the bucket itself (via your provider's
console/API) before Auto-Backup-Manager writes to it; this project does not
configure Object Lock for you.

## Reconnecting

Access/secret keys don't expire the way OAuth tokens do. If a key is
rotated, re-run `abm storage add` with the same `--name` to update it.
